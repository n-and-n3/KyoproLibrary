# 64-bit 素数判定・素因数分解

Codon 0.19.3 用は [Codon/factorize.py](Codon/factorize.py)、PyPy 3.11 用は [PyPy/factorize.py](PyPy/factorize.py)。両方とも `is_prime(n) -> bool` と `factorize(n) -> list[int]` を公開する。`factorize` の結果は重複を含む昇順の素因数列で、`factorize(1) == []`。Codon 版は `1 <= n <= 10**18`、PyPy 版は `1 <= n < 2**64` を扱う。素数判定は 0 と負数に対して `False` を返す。

多数の素数判定だけを行い、素数候補が多い場合は、別の [Codon/is_prime_fast.py](Codon/is_prime_fast.py) と [PyPy/is_prime_fast.py](PyPy/is_prime_fast.py) にある同名の `is_prime` が速い。Forišek–Jančina の FJ32_256 と FJ64_16k ハッシュ表を使い、素数に対する Miller–Rabin を 32-bit 範囲では 1 回、64-bit 範囲では 3 回に減らす。約 145–200 KB のソースが増えるので、分解ライブラリには組み込んでいない。Codon 高速版は単一ファイルで完結している。合成数ばかりの `many_liars` では通常版より遅い場合もあった。

Codon には 4.2 KB の [Codon/is_prime_bpsw.py](Codon/is_prime_bpsw.py) もある。底 2 の強い Miller–Rabin と Selfridge の強い Lucas テストを組み合わせた単一ファイルで、`0 <= n <= 10**18` 用の `is_prime(n)` を公開する。ハッシュ表が必要ない小さいコードとして使える。

[Codon/is_prime_compact.py](Codon/is_prime_compact.py) は 7.5 KB で、`n < 2**32` に FJ32_256、それ以上に BPSW を使う。同じ `is_prime(n)` を公開し、公式ケースでは約 200 KB の FJ 全表版に近い速度だった。短さと速度を両立したい場合の選択肢である。

## 採用した方法

- 小さい素数で先に割り、残りを [決定的 64-bit Miller–Rabin](https://miller-rabin.appspot.com/) で判定する。小さい範囲では `{2,7,61}`、それ以外では 7 基底を使う。
- Codon の Miller–Rabin では基底が `n` 未満なら余分な剰余を取らない。公式の素数中心ケースを同一プロセス内で交互に測ると、判定部分が数 % 速くなった。
- 判定中に `x² ≡ 1 (mod n)` かつ `x ≠ ±1 (mod n)` となったら `gcd(x−1,n)` で因数を取り出す。例: `5461 = 43 × 127` では底 2 の途中で `x = 128` となり、`128² ≡ 1 (mod 5461)` と `gcd(127, 5461) = 127` から因数が得られる。合成数の証拠となった最後の `x` についても `gcd(x−1,n)` を試す。因数が出ない場合は、近い因数向けの短い Fermat 法を試し、残りを [Brent 版 Pollard rho](https://maths-people.anu.edu.au/~brent/pub/pub051.html) で分解する。
- Codon では 64-bit Montgomery 乗算、PyPy では組み込みの `pow(a,b,n)` と `math.gcd` を使う。rho の積は Codon で最大 256 回、PyPy で最大 512 回ごとに gcd を取る。

Codon の Montgomery 乗算メソッドに `@inline` を付けると、追加の半素数 20,000 件の 5 回の交互測定で毎回約 2～8% 速くなった。公式分解ケースではほぼ同速で、通常版の素数判定 10 万件では数 % 遅い場合もあった。多数の素数判定には上記の専用高速版を使う。

PyPy の gcd 間隔は 64、128、256、512、1024 を比較した。公式の大きな半素数 400 個と追加の半素数 1,000 個を、各入力で同じ乱数初期値にそろえ、各実装を交互に呼ぶ測定で 512 回を選んだ。法が `2**31` 未満か `2**63` 以上のときは `pow(y,2,n)` から `y*y%n` に切り替える。30-bit 前後の半素数 10,000 個では約 0.25 秒から 0.18 秒へ短縮した。PyPy 7.3.20 では `2**63` を超えると `pow` が急に遅くなり、`10**19` 付近の半素数 100 個で約 20 秒から約 3.5 秒になった。変更後は 1,000 個を約 35 秒で分解した。中間の法では `pow(y,2,n)+c` の後を条件付き減算にすると、通常の剰余より 2～4% 速かった。

PyPy の分解では、最初に 300 未満の素数で割り、残りの因子の Miller–Rabin では小素数の試し割りを省く。試し割り中に `p*p > n` となった場合は、その時点の残りが素数と確定する。公式 2,635 件では 37 以下の素数だけを使う版の rho 呼び出し 1,598 回から 1,018 回に減った。同じ 300 未満の試し割りを使う条件で因数抽出を無効にすると 1,421 回、非自明な平方根だけから抽出すると 1,300 回、最後の証拠からも抽出すると 1,018 回だった。100、300、1,000 を上限とする交互測定では 300 が概ね良好で、大きな半素数での余分な除算も比較的小さかった。Codon でも同じ拡張を試したが、公式ケースの実行時間が約 1.3 秒から約 1.35 秒へ伸びたため採用しなかった。

## 検証

[Library Checker の公式ジェネレータ](https://github.com/yosupo06/library-checker-problems)を 2026-11-07 に実行した。`factorize` 31 ファイル、計 2,635 数、`primality_test` 13 ファイル、計 801,129 数について Codon・PyPy の出力が公式解と一致した。さらに 20,000 個の半素数、2,000 個の大きな素数冪、1～1,000,000 の全整数でも両方の因数列を確認した。高速素数判定、Codon の BPSW 版、小容量版も全 13 ファイルで一致した。`many_liars` の 10 万合成数には底 2 の強い Miller–Rabin を通過するものが 16,812 個あり、Codon BPSW はすべて合成数と判定した。Codon BPSW 版と小容量版は 100 万以下の全整数と、ランダムな 20 万整数でも通常版と一致した。小容量版の FJ32 部分は 32-bit 乱数 100 万個も通常版と一致した。Codon 高速版は `10**18` 以下の乱数 100 万個でも通常版と一致した。PyPy の通常版と高速版は 100 万以下の全整数で独立した篩と一致し、高速版はランダムな 64-bit 整数 1,000,000 個でも通常版と一致した。PyPy の通常版は `2**64-1` の分解、`2**64-59` の素数判定、さらに 64-bit 上限付近の半素数 200 個の分解を 5 種類の乱数種で確認した。Codon の Montgomery 乗算は 10 万組の乱数について `u128` の直接計算と照合した。

非自明な平方根からの因数抽出は、分解ケースの最初の 2,635 数に対して 95 回成功した。うち 93 回は Carmichael ケースで、大きな半素数 400 個では 0 回だった。最後の Miller–Rabin 証拠の `gcd(x−1,n)` は最初の 2,635 数で追加の 127 回成功し、大きな半素数では 0 回だった。小素数 12 個だけで割る同一条件の PyPy 比較では、公式 2,635 数全体の rho 呼び出しが抽出なし 2,022 回、平方根からの抽出あり 1,901 回、最後の証拠からの抽出もあり 1,598 回だった。Carmichael 100 件だけでは平方根からの抽出によって 82 回対 200 回となり、分解時間は約 4 割減った。`gcd(x+1,n)` も足すと rho は 1,569 回に減ったが、追加の gcd 費用に見合う安定した時間短縮は得られなかった。現行の 300 未満の試し割りを使う条件では、Carmichael 100 件の rho 呼び出しは因数抽出なしの 200 回から抽出ありの 4 回へ減り、大きな半素数 400 件はどちらも 400 回だった。この工夫は構造のある合成数には効くが、最も重い半素数を速くする中心策にはならない。

近い因数を持つ `big2` 系では、Fermat 法を 32 回試すと 400 個中 312 個、128 回なら全 400 個を rho なしで分解した。128 回に変更した結果、PyPy の `big2` 全 400 件の関数実行時間は約 0.28 秒から約 0.02 秒になった。平方数の 16 による剰余を先に調べることで、離れた因数を持つ 400 件の前処理も 100 回反復で約 0.8 秒から約 0.25 秒になった。

指定された [Baillie–PSW の記事](https://note.com/vunu/n/n273765af77d6)に対応する強い Lucas テストも調べた。[Baillie・Fiori・Wagstaff の論文](https://doi.org/10.1090/mcom/3616)には、この組み合わせの反例が `2**64` 未満では見つからなかったという網羅的な検証結果があり、一般の整数について反例が存在しないかは未解決とある。論文では Selfridge 法 A と A* の強い Lucas 判定の結果が同じことも示されており、Codon 版は A を使う。PyPy 試作の公式 `all_prime` 10 万件の関数本体は BPSW が約 1.39 秒、7 基底 Miller–Rabin が約 0.5–0.7 秒で、採用しなかった。一方 Codon では BPSW が 7 基底版の約 2 倍速く、`all_prime` 10 万件では FJ ハッシュ表版より数 % 遅い程度だったので、小さいコードの選択肢として追加した。小さい素数による事前除算を 12 個から 4 個に減らすと、素数中心ケースがさらに約 15% 速くなった。分解後に多い `10**9` 付近の素数は 3 基底 Miller–Rabin の方が速いため、分解ライブラリには組み込んでいない。これらは今回の実装と入力での比較である。SQUFOF と Pollard p−1 も大きな半素数で試したが、今回の実装では rho より速くならなかった。18 桁の整数に一般数体篩法を使う意義は小さく、[FLINT の 64-bit 分解方針](https://github.com/flintlib/flint/blob/main/doc/src/algorithms/number-theory/integer-factoring.md)も rho、Hart 法、SQUFOF の組み合わせである。

オンラインの最速提出は 2026-11-07 時点で、[factorize](https://judge.yosupo.jp/submissions/?problem=factorize&order=%2Btime&status=AC) が C++ 13 ms、PyPy 237 ms、[primality_test](https://judge.yosupo.jp/submissions/?problem=primality_test&order=%2Btime&status=AC) が C++ 30 ms、PyPy 331 ms。Codon の提出言語は Library Checker にない。ローカル値とオンライン値は CPU・入出力が違うため直接比較しない。

[公開されている最速 PyPy `factorize` 提出 #252020](https://judge.yosupo.jp/submission/252020)の関数部分と今回の PyPy 版を、同じ PyPy 7.3.20 プロセスで公式 2,635 数に交互に適用した。両者の出力は公式解と一致し、関数本体の CPU 時間は今回の版が 0.64～0.70 秒、公開版が 1.85～2.00 秒だった。最速提出の判定時間は単一テストファイルでの最大値で、これらの全ファイル合計値とは測定対象が異なる。

ローカルの関数本体だけを測ると、Codon の `all_prime` 10 万件は通常版が約 0.44 秒、高速版が約 0.25 秒だった。小容量版は高速版より数 % 遅い程度だった。PyPy の同ケースは通常版が約 0.5 秒、高速版が約 0.25–0.4 秒だった。Codon 高速版と小容量版は `n < 2**31` に 32-bit Montgomery 演算を使う。同じ素数 `1000000007` を 10 万回判定した場合、従来の 64-bit 演算が約 47 ms、32-bit 演算が約 23 ms だった。実際の提出速度は入力・出力方式にも左右される。
